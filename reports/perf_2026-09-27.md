# Performance — gate cache, query memo, regex tokenize (2026-09-27)

**What changed** (the three changes proposed in `reports/project_review_2026-09-25.md` §9.3):

1. **Document-pair gate cache.** `figure_text.document_pair_gate` caches its raw statistic and null list under `link.figure_text.gate_cache_dir`. The key covers the figure and text contents, seed, shuffle count, the encoder's model, device and normalisation, and the numpy/torch/transformers/sentence-transformers versions. z and the verdict are recomputed from the cached values, not stored. Only encoders that declare their model are cached (`default_encoder` now tags its closure), so test stubs never cache.
2. **Query memo.** `index.memoised` memoises single-text encoder calls on the exact string and returns a copy each time. `compare_retrieval` uses it, so each question is encoded once rather than once per mode. Batch calls pass through, because batch composition changes the floats by about 1e-7.
3. **Regex tokenize.** `index.tokenize` is `re.findall(r"[^\W_]+", text.lower())` instead of a per-character generator.

**Reading.**
- **The gate cache is the large win.** It removes the gate's share of `build_links` (78 % in the review's profile) on any run after the first. A cold run does the same work plus one cache write.
- **The query memo halves `compare_retrieval`,** because the 50 query encodes become 25.
- **The regex tokenizer saves about 3 ms per index load.** That is ~3 % of a warm ask; generation, which needs a paid call, is excluded.
- **Scope of the "before" numbers.** They are taken under the latency rule, so they supersede the indicative, loaded-machine figures in the review's §9.2, which carried no times.
